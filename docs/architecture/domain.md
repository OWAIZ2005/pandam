# PANDAM — Domain & database foundation

Phase 1 built the production-quality **domain foundation**: the relational
schema, Drizzle models, D1 migrations, shared types, Zod validation, a thin
repository layer, the deterministic matching engine, the offer / barter-
transaction lifecycles, and the `/api/v1` route structure. It did **not** build
the marketplace UI, authentication, AI, credits or payments.

## 1. Database architecture

- **Engine:** Cloudflare D1 (SQLite at the edge), bound to the Worker as
  `env.DB`. Accessed only through Drizzle ORM. No Postgres, no Supabase.
- **Schema location:** `packages/database/src/schema/` — one file per aggregate,
  re-exported from `schema/index.ts`. Enum value tuples live in
  `packages/database/src/enums.ts` (a dependency-free leaf module) so
  `@pandam/validation` and the Expo app can share them without bundling Drizzle.
- **Identifiers:** every primary key is an application-generated, prefixed,
  URL-safe string — `<prefix>_<32 hex>` (e.g. `usr_…`, `lst_…`, `btx_…`). See
  `src/id.ts` (`newId`, `isId`). Prefixes make ids self-describing and prevent
  cross-entity mix-ups.
- **Timestamps:** epoch **milliseconds**, stored as `integer`, end to end (DB →
  domain → JSON). `created_at` defaults in SQL (`unixepoch('subsec') * 1000`);
  `updated_at` is refreshed by the repository layer on every write (SQLite
  cannot auto-update a column).
- **Integrity:** `text` enum columns are backed by `CHECK` constraints;
  foreign keys use `ON DELETE cascade | restrict | set null` per relationship;
  natural keys use `UNIQUE` indexes (case-insensitive for `email` / `username`).
- **Migrations:** generated by `drizzle-kit generate` into
  `packages/database/migrations/`, applied with
  `wrangler d1 migrations apply pandam-db --local` (or `--remote` later). Never
  hand-edited. `0000_init` = internal `_meta`; `0001_domain_foundation` = the 16
  domain tables.
- **Seed:** `packages/database/seed/categories.sql` (idempotent) +
  `src/seed.ts` (`CATEGORY_SEED`, `toSlug`). Not applied automatically.

## 2. Domain entities

| Entity                  | Table                       | Purpose                                                                                           |
| ----------------------- | --------------------------- | ------------------------------------------------------------------------------------------------- |
| User                    | `users`                     | Authenticated account. `email` is the auth identifier; no credentials stored here.                |
| Profile                 | `profiles`                  | 1:1 public profile. Coarse location only (city/region/country strings).                           |
| Category                | `categories`                | Curated, stable classification. `slug` is the normalised matching key.                            |
| Listing                 | `listings`                  | **"I HAVE"** — a product / service / skill offered.                                               |
| ListingImage            | `listing_images`            | Image _metadata_ (R2 object key + order). No binary, no upload here.                              |
| Need                    | `needs`                     | **"I NEED"** — same shape as a listing, so HAVE ↔ NEED compare on one axis.                       |
| Match                   | `matches`                   | A discovered **direct reciprocal** candidate (four item ids). No score.                           |
| Offer                   | `offers`                    | A barter proposal: "my `offeredListing` for your `requestedListing`".                             |
| Conversation            | `conversations`             | A negotiation thread, optionally linked to one offer.                                             |
| ConversationParticipant | `conversation_participants` | Membership join table (composite PK), never an array column.                                      |
| Message                 | `messages`                  | A message in a conversation. `editedAt` / `deletedAt` are soft markers.                           |
| BarterTransaction       | `barter_transactions`       | The exchange realised from an accepted offer. **Not monetary** — no amount/currency fields exist. |
| Review                  | `reviews`                   | Feedback tied to a completed transaction. UNIQUE(txn, reviewer).                                  |
| Notification            | `notifications`             | Durable per-user notification record + read state. No delivery here.                              |
| Report                  | `reports`                   | Abuse report about a polymorphic subject (`subjectType` + `subjectId`).                           |
| Dispute                 | `disputes`                  | A dispute about one barter transaction, with its own lifecycle.                                   |

## 3. Entity relationships

```
User 1───1 Profile
User 1───* Listing *───1 Category
User 1───* Need    *───1 Category
Listing 1───* ListingImage

Match  *───1 User (A)   *───1 User (B)
       ├── aListing → Listing   (A HAS)   ├── bNeed → Need   (B NEEDS)
       └── bListing → Listing   (B HAS)   └── aNeed → Need   (A NEEDS)

Offer  *───1 fromUser   *───1 toUser   ?───1 Match
       ├── offeredListing   → Listing
       └── requestedListing → Listing
Offer 1───? Conversation 1───* ConversationParticipant *───1 User
Conversation 1───* Message *───1 User (sender)

Offer 1───1 BarterTransaction
BarterTransaction *───1 initiator (User)   *───1 counterparty (User)
BarterTransaction 1───* Review  *───1 reviewer (User)  *───1 reviewee (User)
BarterTransaction 1───* Dispute *───1 raisedBy (User)

Report *───1 reporter (User)   → (subjectType, subjectId) polymorphic
Notification *───1 User
```

`ON DELETE`: user-owned content cascades from `users`; `category` deletes are
`restrict`ed (categories are curated); `offer → conversation` / `offer → match`
links are `set null`; `barter_transaction → offer` and the transaction's user
refs are `restrict` (history is preserved).

## 4. Matching model — deterministic, rule-based, no AI

`apps/worker/src/domain/matching.ts` is a **pure function**:

```
findReciprocalMatches(listings: MarketItem[], needs: MarketItem[]): ReciprocalMatch[]
```

A `MarketItem` is `{ id, ownerId, categoryId, type }`. A match exists iff:

```
user A HAS x   AND   user B NEEDS x        with x = (categoryId, type)
user B HAS y   AND   user A NEEDS y        with y = (categoryId, type)
```

- The comparison key is `${categoryId}::${type}` — a **stable id**, never
  free-form text. "Web Design" / "web design" / "WEB DESIGN" collapse to the
  single `web-design` category upstream, so they match.
- `x` and `y` may be the same key or different keys.
- A user never matches themselves.
- Output is deterministic: sorted, de-duplicated, each pair emitted once with
  `userAId < userBId` (lexicographic).
- **No** embeddings, vector search, semantic similarity, LLMs or scoring. If a
  score is ever added it must stay explainable and deterministic.
- The `matches` table only _persists discovered candidates_ (so users can
  dismiss them and an offer can reference the exact four items). Compatibility
  is computed, not invented.
- Extensibility without AI: refine the key with a future
  `listing_attributes` / tag table — the matcher signature does not change.

`GET /api/v1/matches` wires this to the repository layer: it loads every
published listing/need, runs the matcher, and returns the candidates involving
the current user.

## 5. Offer lifecycle

`apps/worker/src/domain/offers.ts` — pure state machine.

```
pending ──accept──▶ accepted    (recipient)
pending ──reject──▶ rejected    (recipient)
pending ──cancel──▶ cancelled   (sender)
pending ──expire──▶ expired     (system, once past expiresAt)
```

`pending` is the only non-terminal state. `offerTransition(current, action)`
returns `{ ok: true, next }` or `{ ok: false, error }` — it never throws.
`isOfferExpired(offer, nowMs)` is the expiry predicate. Authorization (who may
accept vs. cancel) is enforced at the route layer, separately from the state
machine.

## 6. Barter transaction lifecycle (non-monetary)

`apps/worker/src/domain/barter.ts` — pure state machine. A transaction is
created from an **accepted offer** and tracks the physical exchange. There is no
money: the table has no amount, currency, fee or balance column, and the type is
named `barter_transactions`.

```
created ──start──▶ in_progress ──complete──▶ completed   (terminal)
   │                    │
   └──────cancel────────┴──▶ cancelled                   (terminal)
                        │
                     dispute ▼
                     disputed ──resolve_in_progress──▶ in_progress
                              └─resolve_cancelled────▶ cancelled
```

`barterTransition(current, action)` mirrors the offer machine's contract.

## 7. Review integrity

`apps/worker/src/domain/reviews.ts` — `canReview({ transaction, reviewerId,
revieweeId, reviewerHasReviewed })` returns `{ ok: true }` or `{ ok: false,
reason }`. A review is valid only when the transaction is `completed`, the
reviewer was a party, the reviewee is the _other_ party, and the reviewer has
not already reviewed. The DB backs this with `FK(transactionId)`,
`UNIQUE(transactionId, reviewerId)`, `CHECK(reviewer <> reviewee)` and
`CHECK(rating BETWEEN 1 AND 5)` — so a fake review cannot even be represented.

## 8. API structure

Base path **`/api/v1`** (Hono, `apps/worker/src/routes/api/v1/`).

| Route                                                                                                              | Status                                                                                   |
| ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `GET /api/v1`                                                                                                      | ✅ machine-readable description of the surface                                           |
| `GET /api/v1/categories`                                                                                           | ✅ list active categories (DB-backed)                                                    |
| `GET /api/v1/matches`                                                                                              | ✅ reciprocal candidates for the current user (auth required)                            |
| `/api/v1/{users,profiles,listings,needs,offers,conversations,messages,transactions,reviews,notifications,reports}` | mounted, return **501 `not_implemented`** — planned endpoints documented in `planned.ts` |

- **Response envelopes** (`apps/worker/src/lib/http.ts`, matching `@pandam/types`):
  success `{ ok: true, data }`, failure `{ ok: false, error: { code, message,
details? } }`. `ApiError` carries a code → HTTP status map. The global
  `onError` converts any unexpected throw to `internal_error` — **no stack
  traces, secrets or DB internals reach the client**.
- **Validation:** request bodies are parsed with the shared Zod schemas
  (`@pandam/validation`); failures become `422 validation_error` with
  field-level `details` via `zodDetails`.
- **Auth (NOT built):** `apps/worker/src/context.ts` — `resolveUserId(c)` reads
  a **development-only** `x-pandam-user-id` header when `PANDAM_ENV !==
'production'`; `requireUserId(c)` throws `401` when absent. A later phase
  replaces this with a real provider that verifies a token and injects the id.
- **Ownership / mass-assignment:** repositories accept explicit `Create*`/
  `Update*` input types (no spreading of arbitrary request bodies); routes are
  responsible for ownership checks before mutating. Drizzle parameterises every
  query (no SQL injection).

## 9. Why V1 has NO AI matching

Barter compatibility in V1 is a **structural fact** (reciprocal category+type),
not a prediction. A deterministic rule is explainable ("you both want what the
other has, in _Photography_ and _Web Design_"), debuggable, free to run, and
needs no training data, vector store or model budget. The matcher is a pure
function behind a stable signature, so an ML-backed implementation can be added
later as a _separate_ strategy without touching the schema or the offer flow.

## 10. Why V1 has NO credits / currency / payments

PANDAM V1 is **direct barter only**: a good/service is exchanged for another
good/service. There is deliberately no wallet, balance, credit, token, price,
fee, Stripe, crypto or multi-party chain — and the schema has no column that
could hold one. `Offer` and `BarterTransaction` are their own aggregates, so if
a credits system is ever introduced it is additive, not a rework.

## 11. Cloudflare infrastructure boundaries

| Concern                         | Where it lives                     | Status                                                                                   |
| ------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| Relational data                 | D1 + Drizzle (`packages/database`) | schema + migrations built; **no cloud DB provisioned** — local SQLite under `.wrangler/` |
| Object storage (listing images) | R2, mediated by the Worker         | binding documented (commented) in `wrangler.jsonc`; `listing_images` stores keys only    |
| Realtime chat                   | Durable Objects + WebSockets       | binding documented (commented); `conversations` / `messages` are plain relational rows   |
| Background jobs                 | Queues                             | binding documented (commented)                                                           |

No `wrangler d1 create` / `r2 bucket create` / `queues create` was run. The
Worker never talks to D1/R2/DO/Queues except through the repository layer /
future infrastructure adapters.
